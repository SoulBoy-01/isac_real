# Q002　既然定长能保边界，为什么不用 MPEG-TS 传实时视频

> 日期：2026-10-23
> 提问背景：学完积木 1–4 后，作者由"定长边界不会被误码破坏"推出"应当用 MPEG-TS"
> 重要性：**这很可能是答辩时被问到的第一个技术问题**

---

## 我的提问（原文）

> 那按照这个道理，难道不应该是用 MPEG-TS 去传输实时视频流更合适吗？

---

## 先判断：这个推理对在哪

**推理方向完全正确。**

作者的逻辑链：

```
前提 1：边界信息放在数据里，就会被打坏
前提 2：MPEG-TS 是定长，边界由算术决定
结论：MPEG-TS 的边界不会被打坏 → 应该用 MPEG-TS
```

**前提 1 ✅ 正确，前提 2 ⚠️ 不完整，所以结论 ❌ 不成立。**

问题出在前提 2 —— MPEG-TS 并不是"纯定长"。

---

## 核心更正：MPEG-TS 是"定长 + 分隔符"

### 188 字节的格子，必须先知道从哪开始

定长包有个隐含前提：**必须知道第一个字节在哪**。

示例：如果收到一串字节，怎么知道"第 0 个包"从哪个字节开始？

```
... 00 47 1F FF 10 47 00 47 1F FF 10 47 ...
        ↑        ↑     ↑
   哪些是真同步字节？哪些是载荷里的 0x47？
```

**MPEG-TS 的答案是：每包第 1 字节放 `0x47`，然后验证 188 字节之后还是不是 `0x47`。**

> **依据**：ISO/IEC 13818-1 附录 B。接收端同步流程：
> 1. 逐字节搜索 `0x47`
> 2. 检查 188 字节后是否仍为 `0x47`
> 3. 需连续 3–5 次成功才判定"锁定"
> 4. 若中途失败，回到步骤 1

**所以 `0x47` 就是分隔符。** 每 188 字节出现一次。

### 这个结论的后果

| 判断 | 说明 |
|---|---|
| MPEG-TS 的边界**不能**仅靠算术恢复 | 必须靠 `0x47` 重新定位 |
| `0x47` **在数据里** | 会被误码破坏 |
| 破坏概率 | 每个 `0x47` 被打中概率 ≈ p；一个 1316 字节 UDP 包含 7 个 → **约 7p** |

**这跟 2 字节长度前缀被打坏，是同一个数量级的问题。**

---

## 关键区分：两种"定长"

| | 边界由什么决定 | 需要找标记吗 |
|---|---|---|
| **MPEG-TS** | 找到 `0x47` 后按 188 走 | **需要**（每包都要验） |
| **M3 定长分片** | "这是第 N 个块，从 `N × 1024` 开始" | **不需要** |

### 为什么 M3 不需要找

因为**边界格子与传输块对齐**：

- 物理层交付的是"第 N 个 1024 字节块"
- 应用层直接按这个块处理
- 块长由配置给出，不写在数据里
- **没有任何"标记"需要扫描确认**

**这是 M3 失步率为 0 的真正原因**——不是"它用了定长"，而是"**它的定长格子不需要重新定位**"。

### 一句话表述（论文可用）

> **"定长"本身不足以保证免于失步；只有当边界格子与传输块对齐、无需任何标记重新定位时才成立。**

**这句话比"定长比长度前缀好"精确得多，也是本文 M3 设计的理论依据。**

---

## 第二个问题：开销

| 项目 | MPEG-TS 的开销 | 依据 |
|---|---|---|
| 包头 | 4 / 188 = **2.13%** | ISO/IEC 13818-1 |
| PAT/PMT 表 | 周期性重发，约 0.5–1% | 同上 |
| PCR 时钟 | 每 100 ms 至少一次 | 同上 |
| **空包填充（null packet）** | **变码率视频下可达 10–30%** | 同上（PID 0x1FFF） |

### 最后一条是致命的

MPEG-TS 要求**恒定码率（CBR）**，而视频是**变码率（VBR）**：

```
I 帧（约 15 KB）到来 → 码率高 → 不补空包
P 帧（约 3 KB）到来 → 码率低 → 疯狂补 null packet 填满
```

**null packet 是无用数据，却占满了空口。**

而 M1/M2/M3 都不要求恒定码率——有几个字节发几个字节。

---

## 第三个问题：缓冲模型与时钟耦合

### T-STD 缓冲模型以秒计

> **依据**：ISO/IEC 13818-1 附录 D 定义 T-STD（Transport Stream System Target Decoder），音频/视频解码缓冲以秒计。

MPEG-TS 为**广播**设计，假设接收端有**大缓冲**（观众晚几百毫秒无感）。

**本文业务的约束是 250 ms 端到端**。一个"假设你缓冲几秒"的标准，与"要求你不许缓冲"的业务，在设计目标上对立。

### 时钟耦合是 VLC 死锁的原因

VLC 这类播放器把解码节奏耦合到 **PCR（Program Clock Reference）** 上。

PCR 一坏 → 播放器不是"跳过继续"，而是**卡死等时钟恢复**。

**这就是实测 500 倍放大的机制解释。**

---

## 第四层：实测数据（最有力的证据）

| 传输栈 | 放大因子 γ | 主导机制 |
|---|---|---|
| **MPEG-TS + VLC** | **≈ 500×** | 同步搜索滞留 + PCR 时钟死锁 |
| MPEG-TS + ffplay | ≈ 150× | 有界同步搜索，无死锁 |
| 裸流 + ffplay | ≈ 8× | 偶发帧级连锁 |
| **裸流 + GStreamer** | **≈ 4×** | 起始码风险，静默跳帧 |

**相差 125 倍。**

> 理论可以争论，数据不会。**这组数据本身就是对"该不该用 MPEG-TS"的回答。**

**注意方法学要点**：四组实验用的是**同一份物理误码流**，唯一的差别是容器与解码器。这是能下因果结论的前提。

---

## 标准应答（答辩背这一段）

> MPEG-TS 采用 188 字节定长包，表面看边界由算术决定。但其接收端仍须靠 `0x47` 同步字节重新建立 188 字节网格，一旦同步字节被误码破坏即失锁，需重新扫描；加之其为恒速率广播设计，需以空包填充吸收变码率波动，且缓冲模型（T-STD）以秒计，与实时业务的百毫秒级时延约束相冲突。
>
> 因此定长的优势只有在**边界格子与传输块对齐、无需任何标记重新定位**时才能兑现——这正是本文 M3 模式的设计出发点。
>
> 实测也支持这一点：在同一误码流下，MPEG-TS + VLC 的等效放大因子约为裸流 + 容错解码器的 125 倍。

## 这一轮新增的概念

| 术语 | 英文 | 含义 |
|---|---|---|
| 同步字节 | sync byte | MPEG-TS 每包首字节 `0x47`，用于重建包网格 |
| 恒定码率 | CBR（Constant Bit Rate） | 码率不随时间变化 |
| 变码率 | VBR（Variable Bit Rate） | 码率随内容变化（视频天然如此） |
| 空包 | null packet | PID 0x1FFF 的填充包，用于维持 CBR |
| T-STD | Transport Stream System Target Decoder | MPEG-TS 的解码缓冲理论模型（秒级） |
| PCR | Program Clock Reference | TS 中的时钟参考，用于同步解码 |
| 网格重建 | grid reconstruction | 从字节流中重新找到 188 字节格子起点 |

## 三个对照，便于复习

### 对照 1：三种"定长"的差别

| 方案 | 格子长度 | 如何确定起点 | 误码能否破坏 |
|---|---|---|---|
| MPEG-TS | 188 | **扫 `0x47`** | **能**（7p/包） |
| M3 定长分片 | 1024 | **传输层告知块序号** | **不能** |
| 假设的"无同步定长" | 188 | 无从确定 | — |

**结论**：定长只是必要条件，"边界与传输块对齐"才是充分条件。

### 对照 2：三个设计目标的冲突

| | MPEG-TS 假设 | 本文业务要求 |
|---|---|---|
| 码率 | 恒定 | 可变 |
| 缓冲 | 秒级 | ≤250 ms |
| 时钟 | 有 PCR，播放器跟随 | 无时钟，尽快丢弃 |

**三项全部冲突。** 所以不是"TS 不够好"，而是"TS 为另一个问题设计的"。

### 对照 3：开销对比

| 方案 | 每包额外开销 | 能否防失步 |
|---|---|---|
| MPEG-TS | 4 字节头 + 空包填充（可达 30%） | 部分（靠 `0x47`） |
| M1 裸前缀 | 2 字节 | 否 |
| M2 前缀+CRC | 4 字节 | 部分（能检出） |
| **M3 定长分片** | **2 字节（序号）** | **是** |

**M3 用 2 字节实现了 MPEG-TS 用 4 字节 + 空包填充都没做到的事。**
