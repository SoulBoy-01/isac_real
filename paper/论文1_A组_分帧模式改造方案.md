# A 组分帧模式改造方案（论文 1 核心实验的使能工作）

> ⚠️ **代码基线声明**：本方案依据 `D:\isac\OpenISAC_new` 的**提交 `e3de1c2` 之后的本地副本**写成。
> 设备上的源码可能已另行调整，**落地前必须先与设备代码对齐**（见《设备代码同步方案》）。
> 在完成对齐前，本文档只作为**设计草案**，不要直接套用行号。

> 目的：让"变长前缀 / 定长分片 / 前缀+CRC"三种分帧方式可在同一链路上切换，
> 从而证明**失效来自分帧元数据，而非纠错强度**。
> 前置：无需硬件即可完成离线验证；上链路只需换一个模式开关。

---

## 一、要证明什么（先锁定结论，再谈实现）

| 命题 | 实验 | 判据 |
|---|---|---|
| P1 长度字段是单点故障 | 变长前缀 + 无外码，翻 1 bit | 失步率 ≫ 基线 |
| P2 固定边界可消除该失效 | 定长分片 + 无外码 | 与"有外码"无显著差异 |
| P3 局部校验即可兜底 | 前缀 + CRC，CRC 错则丢包 | 失步率接近定长组 |
| P4 不是"带宽不够" | 三组同码率、同位置 | 排除竞争解释 |

**P4 是审稿人一定会问的**：三组必须同码率，只差分帧方式。

---

## 二、三种模式的线上格式

现有实现（`OFDMModulator.cpp:1126-1140`）：

```
[2B 大端长度][原始载荷]  →  RS(255,K)  →  LDPC  →  空口
```
接收端（`OFDMDemodulator.cpp:2108-2128`）从 `rs_decoded[0..1]` 读长度后切包。

### 模式 1：`prefix`（现状，作为对照组）

```
[2B len][payload]                     无保护
```

### 模式 2：`prefix_crc`（局部兜底）

```
[2B len][2B CRC16(len)][payload]
```
接收端：先校验 CRC。
- CRC 通过 → 按 len 切包，正常投递；
- CRC 失败 → **丢弃该块**（计数器 +1），不做盲目切分。

关键：把"全局错位"降级为"局部丢一块"。这是 P3 的实现基础。

### 模式 3：`chunked`（固定边界）

```
[2B seq][1022B 字节流片段]            固定 1024 B，不携带长度
```
接收端：块长由配置固定，不需要长度字段；`seq` 只用于**检测缺口**，不用于切分。
即使 seq 被翻错，块边界依然正确 → 这是 P2 的实现基础。

> ⚠️ 注意：`chunked` 丢弃了 UDP 报文边界，把视频当作**连续字节流**处理。
> H.264 Annex B 本身是自定界的（起始码），因此可行，但需要解码端确认（见第五节 A1/A2）。

## 三、改哪里（文件 / 函数 / 行号）

### 1. 编码侧：`src/OFDMModulator.cpp`

- `_encode_and_enqueue_payload()`，约 **1115–1140 行**
  - 现在是：push 2 字节长度 → `_rs.encode()`
  - 改为按 `_framing_mode` 分支：

```cpp
switch (_framing_mode) {
case Framing::Prefix: {                    // 现状
    rs_input = [len_hi, len_lo] + payload;
    break;
}
case Framing::PrefixCrc: {
    uint16_t crc = crc16_ccitt(&len_hi, 2);
    rs_input = [len_hi, len_lo, crc_hi, crc_lo] + payload;
    break;
}
case Framing::Chunked: {
    // 1024 B 固定块：2 B seq + 1022 B 流片段
    rs_input = [seq_hi, seq_lo] + chunk;   // chunk 恒为 1022 B，末尾补 0x00
    seq++;
    break;
}
}
```

- 新增成员：`Framing _framing_mode; uint16_t _seq;`
- 新增配置项：`framing_mode: prefix | prefix_crc | chunked`（YAML）或编译宏 `-DFRAMING_MODE=2`

### 2. 解码侧：`src/OFDMDemodulator.cpp`

- `RS 外码解码 → 还原原始 UDP 载荷`，约 **2108–2128 行**
  - 现在：`orig_len = rs_decoded[0..1]`，然后 `assign(begin+2, begin+2+orig_len)`
  - 改为分支：

```cpp
switch (_framing_mode) {
case Framing::Prefix:
    // 现状（对照组）
    break;
case Framing::PrefixCrc: {
    uint16_t len = (rs_decoded[0]<<8)|rs_decoded[1];
    uint16_t crc = (rs_decoded[2]<<8)|rs_decoded[3];
    if (crc16_ccitt(&rs_decoded[0],2) != crc) {
        _framing_drop++;                  // 埋点：CRC 拒绝
        return;                           // 丢一块，不切分
    }
    udp_data.assign(rs_decoded.begin()+4, rs_decoded.begin()+4+len);
    break;
}
case Framing::Chunked: {
    uint16_t seq = (rs_decoded[0]<<8)|rs_decoded[1];
    if (_last_seq && seq != (uint16_t)(_last_seq+1)) _seq_gap++;
    _last_seq = seq;
    udp_data.assign(rs_decoded.begin()+2, rs_decoded.begin()+1024);
    break;
}
}
```

### 3. CRC16 实现

放 `include/Framing.hpp`（新文件，约 30 行）：

```cpp
static inline uint16_t crc16_ccitt(const uint8_t* p, size_t n) {
    uint16_t crc = 0xFFFF;
    for (size_t i = 0; i < n; ++i) {
        crc ^= (uint16_t)p[i] << 8;
        for (int b = 0; b < 8; ++b)
            crc = (crc & 0x8000) ? (crc << 1) ^ 0x1021 : (crc << 1);
    }
    return crc;
}
```

## 四、必须加的埋点（否则实验做不出来）

| 计数器 | 含义 | 用途 |
|---|---|---|
| `blocks_total` | 收到的块数 | 分母 |
| `framing_drop` | CRC 拒绝 / 长度非法 | P3 的因变量 |
| `seq_gap` | 序号缺口数 | P2 的因变量 |
| `misalign_events` | 检测到的流级错位（连续 N 块不可解析） | **P1 的因变量，最关键** |
| `bytes_delivered` | 实际投递给解码器的字节数 | 排除"少投递"的解释 |

`misalign_events` 的判定：连续 3 块无法找到 Annex B 起始码 `00 00 00 01`，记一次。

## 五、离线验证（**无硬件即可做，今天就能跑**）

用 Python 写一个 200 行的模拟器：

```
输入：一段真实 H.264 Annex B 码流（你手上的 .h264 就行）
对每个字节以概率 p 翻转（p = 1e-6 … 1e-3）
按三种模式打包 → 模拟 LDPC 通过/失败 → 解包
统计：失步次数、恢复所需块数、可用字节率
输出：失步率 vs p 的三条曲线
```

**这一步的价值**：
1. 在设备回来前就能判断 P1/P2/P3 是否成立；
2. 曲线上链路后只需**验证一个点**（比如 p≈1e-4），不用盲扫；
3. 论文里可作为"解析模型"，实测点作为"验证"——比纯实测更有说服力。

### 附带产出 A1/A2 决策

`chunked` 模式下 GStreamer 是否接受任意 1022 B 的 buffer，需要 10 分钟试：
- **A1**：直接 `udpsink` 固定 1024 B → `udpsrc → h264parse`。若正常，采用。
- **A2**：若 `h264parse` 报 "broken bitstream"，接收端加一个 50 行字节 FIFO，按起始码重切 NAL 再投递。
两者都不改变"无长度字段"这一本质，只是投递方式不同。

## 六、上链路测试步骤（设备回来后，D5–D6 用）

1. 编译三个模式（三个二进制或一个宏三份）
2. 固定：位置、码率 1200 kbps、分辨率、GOP、天线朝向
3. 每模式 5 min × 3 次，顺序随机（避免热漂移偏向某一组）
4. 记录：`blocks_total / framing_drop / seq_gap / misalign_events / 可用帧率 / 恢复时间`
5. 机制验证：发送端人为翻转长度字段 1/2/3 bit，每档 60 s

**顺序随机很重要**——固定顺序会让最后跑的组吃到不同的温度/干扰状态。

## 七、风险

| 风险 | 影响 | 处理 |
|---|---|---|
| `chunked` 破坏 GStreamer 解析 | 该模式不可用 | 走 A2（字节 FIFO 重切 NAL）；实在不行只保留 prefix_crc |
| 定长 1024 B 导致时延增加 | 需要报告 | 测时延，若增加 >20 ms 在论文里说明并权衡 |
| 改动引入新 bug | 实验白做 | 先跑离线单测 + 回环（loopback）自测，再上链路 |
| 三种模式编译管理混乱 | 操作失误 | 用三个 build 目录，二进制名带模式后缀 |
