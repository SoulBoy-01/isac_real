答辩追问整理（修订版）

本版修正了上一版中三处技术错误：LDPC 块的计算口径、libfec 的参数示例、以及"RS 没起作用所以链路能跑"这一与实测冲突的表述。并补入两节：γ 因子的定位（复用还是创新）、p 的实测方法。

1. libfec 是什么

提问：材料里说的 libfec 是什么？

libfec 是 Phil Karn（呼号 KA9Q）编写的一套成熟、开源的前向纠错函数库，以 LGPL 发布。它包含 Reed-Solomon 编解码、卷积码/Viterbi 译码等经典算法，在业余无线电、DVB 与 CCSDS 地面段里被长期使用。

"替换为成熟实现"指的是：放弃自己手写的 RS 编解码，直接调用 libfec 中经过长期验证的函数。这是标准的工程补救——承认实现层有缺陷，但算法本身是标准的，换库即可消除实现风险。

答辩口径："外码算法采用标准 RS(255,K)，实现层改用 libfec；这消除了自研实现的验证风险，也把参数改成运行期可配置，为激活点扫描提供了便利。"

2. γ 因子是复用还是创新

提问：γ 的建模是复用的，只是首次在 ISAC 的通信视频链路上引用，对吗？

对，这个判断是准确的。必须分成两层说，否则会过度声明：

层面是否新颖依据
"封装格式在误码下会放大故障"这一现象不新DVB-H / MPE-FEC 时代已有定量分析；MPEG-TS 的同步字节与连续性计数器脆弱性是公开知识
头部暴露比 28:4 → γ₀≈7 这一量级估算不新本质是"关键字节数之比"，属工程常识的定量表达
在同一物理误码流下，对四种容器/解码器栈做端到端横向实测较新公开文献中，ISAC 链路上没有同类测量
把 γ 用作设计判据（容器/解码器选择优先于外码强度）较新结论反直觉，且可操作
准确的表述："容器误码放大这一现象在广播与流媒体领域已有研究；本工作的贡献不是提出该现象，而是把它引入 ISAC 实时视频链路，并给出同一误码源下的四栈实测与设计判据。"
不要说的两句话：
① "首次提出容器放大因子"——会被立刻反驳；
② "模型预测 7、实测 4–500，验证了模型"——4 到 500 跨两个数量级，不构成验证，只能称"量级一致"。

3. p 怎么实测

提问：γ = P_data_loss / p 里的 p，具体怎么测？

先明确 p 的定义：容器输入端（即 LDPC 译码输出、RS 译码之前）的字节错误率。这个位置决定了测法——不能在 UDP 出口测，因为那里已经过了 RS。

方法 A（推荐）：在 LDPC 输出处打点

  1. 发端用 PRBS 生成载荷：种子固定、按包序号可重建，纯随机字节（不要用 0xA5 填充，也不要混入序号头）。
  2. 收端在解调器里、decode_frame() 返回之后、RS decode 之前，用同一 PRBS 重建期望字节，逐字节比对。
  3. 统计：p = 失配字节数 / 比对字节总数。

好处：直接得到进容器之前的 p，与是否启用外码无关。

方法 B（不改代码）：关外码 + PRBS 在 UDP 接口比对

关掉 RS 后用 PRBS 载荷，在 UDP 出口逐字节比对。前提是同一 SNR、同一调制——因为 p 只由 SNR 与内码决定，不随外码变化。可行，但必须说明"p 在无外码条件下测得，同 SNR 下与外码无关"。

统计要求（这一点常被忽略）

目标相对误差需要的错误事件数 N·pp=10⁻⁴ 时需比对字节数
±30%≈11≈1.1×10⁵
±10%≈100≈10⁶
±3%≈1100≈1.1×10⁷

95% 置信区间：p ± 1.96·√(p(1−p)/N)。给 γ 报数时，p 必须带区间；否则"γ=500"这个数没有误差棒。

P_data_loss 也要定义清楚

建议用坏帧率：1 − 可用帧占比，其中"可用帧"用 VMAF/PSNR 阈值或人工标注判定。不要用"可用播放百分比"这种主观量——评审会问判定规则。

答辩口径："p 在 LDPC 译码输出处用 PRBS 逐字节比对测得，样本量约 10⁶ 字节，给出 95% 置信区间；P_data_loss 用坏帧率度量。γ 是这两者的比值，绝对倍数依赖 p 的实测精度，而跨栈的相对差异（125 倍）对 p 的系统误差不敏感。"

4. GStreamer 实测 4×，和模型 7× 不接近吗

提问：实际用的就是 GStreamer，不是和模型接近吗？为什么说"差两个数量级"？

你的理解是对的。裸流 + GStreamer ≈4×，与模型 γ₀=7 只差 1.75 倍，属于同一量级。"跨两个数量级"指的是四种栈之间的横向差异（4× 到 500×）。

答辩口径："我们实际部署的是 GStreamer 裸流栈，实测约 4×，与模型 γ₀=7 在同一量级，这支持了量级估算的合理性。材料中'跨两个数量级'指四栈横向对比，说明 γ 高度依赖实现栈，不能当作跨栈通用常数。"

补一句更稳的："γ 的绝对值依赖 p 的实测，但跨栈的相对差异与 p 无关。" 这句话能同时挡住"模型没验证"和"p 没测"两个追问。

5. H.264 的 I/P/B 帧与"持续到下一个 I 帧"

提问：错误持续到下一个 I 帧，和 P 帧有关系吗？这些帧分别是什么？

帧类型编码方式参考谁被谁参考
I 帧帧内编码，不参考任何帧无P 帧、B 帧
P 帧前向预测，只编码与参考帧的差异前面的 I 或 P 帧后面的 P、B 帧
B 帧双向预测前后 I/P 帧一般不作为参考（非参考 B 帧）

P 帧正是错误传播的载体：一个 P 帧的参考链断了，它自己解不出来，后面所有直接或间接参考它的帧跟着坏，直到下一个不依赖前帧的 I 帧出现，参考链才归零。GOP=30 @ 20 fps → 最长约 1.5 秒。

要补一句（这是你们的特殊性）："我们的失效不止是单帧坏，而是字节流级失步——前缀错导致后续包边界全错，此时连'I 帧在哪'都解析不出来，恢复要等流重新对齐。"

6. LDPC 块 63 B 与实际占用（本版修正）

提问：63B 是固定值吗？B 是 bit 还是 byte？占用怎么算？

B 是 Byte。 但上一版说"63 字节是系统选定的处理单位"是不准确的——它不是随便选的：

63 B = 504 bit ÷ 8 = LDPC(1008,504) 的信息位长度。内码定成 (1008,504)，信息块就必然是 63 字节，没有选择余地。

占用要分两个口径

KRS 块数RS 后字节LDPC 块数 (⌈/63⌉)信息字节空口字节（码率 1/2，×126）
223512752113232646
191615302515753150

比值 3150/2646 = 1.19，即 K=191 比 K=223 多占约 19% 空口时间。两种口径比值相同，但别说"空口占用 1323 B"——那是信息字节，空口要乘 2。

上一版把 1323 B 说成"空口占用"，被懂行的评审一算就穿帮。

7. RS 外码的真实作用（本版重写）

提问：既然 RS 没在纠错，实时视频为什么能跑？是不是内码够强 + 环境稳态？

这个说法只对了一半，而且漏掉了一个你自己的实验事实。

事实是：不加 RS 外码，稳态下实时视频不可用。 所以"RS 没起作用所以链路能跑"这个推理链是断的。

正确的拆解是把 纠错 和 分帧 分开：

  1. 纠错没生效：译码器因实现缺陷永远判"无错"，从未纠正过任何字节——这部分结论已撤回。
  2. 分帧在起作用：2 字节长度前缀位于 RS 码字内部。去掉外码，前缀裸露，一处比特错误就让长度字段错、整条字节流错位——视频不是"画质变差"，而是"无法解析"。
  3. 内码是第一道防线：LDPC 把误码压到容器与解码器能带伤工作的水平；GStreamer 的容错行为比 VLC 好得多。
一句话口径："RS 有用，但不是以纠错的方式有用——它以码字边界守住了分帧。"
不要说的："RS 没起作用所以链路能跑"——这句会被"那拿掉 RS 为什么崩"一句问死。

8. 换成 libfec 之后，创新点还够吗

提问：自研 RS 换成 libfec，论文创新点会不会不够？目标中文核心。

先说结论：换库不损失创新点，因为"自己写 RS 编解码"本来就不该算创新点。 那是教科书算法，写出来只证明编码能力，不证明研究贡献。换库反而去掉了一个会被攻击的面。

创新点应该这样排

层次内容强度对应章节
场景ISAC 链路上跑连续媒体业务，此前无人系统测量中绪论 / 第 1 章
方法逐层可观测测量 + 同一误码源下的栈间对照中第 2 章
发现容器/解码器放大 ≫ 外码强度；外码守分帧较强（反直觉）第 3–4 章
工程平台改造：多阶 QAM、级联链、视频贯通、队列整形弱—中第 2、5 章

对"中文核心"够不够

要分期刊层次看：

  • EI 中文刊（通信学报、电子与信息学报）：要求理论与方法增量，单靠"我们测了 γ"偏薄，需要激活点曲线 + 共存实验撑起来。
  • 北大核心 / 科技核心（电讯技术、无线电工程、计算机工程、电视技术等）：真实平台 + 完整实验 + 清晰结论就够，你现在的工作量是够的。
但要补两样东西，否则会被当成"测量报告"：
① 一个可复用判据——给定残余误码 p 与可接受坏帧率，如何选容器与解码器；
② 一条定量边界——γ 随栈、码率、误码形态怎么变（一张表或一条曲线即可）。

表述模板（中文核心常用三段式）

针对 ISAC 链路上实时视频业务的可靠传输问题，
提出/构建了 基于容器放大因子 γ 的跨层选型判据，
并在 OpenISAC 平台上完成了四栈实测。
实验表明：容器与解码器的选择对视频可用性的影响，
显著大于外码强度的调整。
论文里必须改掉的表述：把"自主设计并实现了 GF(2⁸) 系统式 RS 编解码器"改为"在开源平台上搭建了 RS–LDPC 级联编码链路，外码采用成熟 FEC 库实现，重点在于链路的可观测改造与参数扫描"。

9. 在 Ubuntu 22.04 上集成 libfec（参数已修正）

提问：部署平台是 Ubuntu 22.04，怎么集成？

上一版的参数是错的：init_rs_char(8, 0x187, 112, 11, 32, 0) 对应的是 CCSDS 标准 RS 码（本原多项式 0x187、首根 112、间隔 11），和你报告里写的 0x11D、根从 α⁰ 起、间隔 1 不是同一个码，互相译不了。

你的正确参数

// RS(255,223)，GF(2^8)，本原多项式 0x11D，根 α^0..α^31
void *rs = init_rs_char(8,      // symsize
                        0x11D,  // gfpoly：与报告一致
                        0,      // fcr：首根 α^0
                        1,      // prim：间隔 1
                        32,     // nroots：t=16
                        0);     // pad：完整码

关于兼容性：收发两端是同时替换的，新旧实现之间不需要互通，只要两端参数一致即可。所以"必须与旧 0x11D 兼容"这个约束并不成立——除非你要和旧采集数据对齐。

换 libfec 的一个实际收益

nroots 是运行期参数。要扫描 t=1/2/8/16 的激活点，只需改这一个数，不用改编译期常量重编译——这正是激活点实验最需要的能力。

安装与链接

# 先确认包名（答辩前务必在你机器上跑一次）
apt-cache search libfec

# 有 dev 包则直接装
sudo apt install libfec-dev

# 编译时链接（库要放在源文件之后）
gcc your_program.c -o your_program -lfec

若走源码：git clone https://github.com/quiet/libfec.git && cd libfec && mkdir build && cd build && cmake .. && make && sudo make install，默认装到 /usr/local。

调用骨架与自检

unsigned char block[255];
// 前 223 字节填数据，后 32 字节留给校验
encode_rs_char(rs, block, &block[223]);

int nerr = decode_rs_char(rs, block, NULL, 0);
// nerr >= 0：纠正的符号数；nerr < 0：不可纠

// 自检：注入 0..16 个错误，必须全部还原且 nerr 等于注入数；
// 注入 17 个，必须返回 -1。
答辩口径："在 Ubuntu 22.04 上优先用发行版 libfec 包做快速替换与单元验证；替换后收发两端使用同一组 GF 参数（0x11D、fcr=0、prim=1），并用注入错误的自检确认 0–16 个错误可纠、17 个报不可纠。"
