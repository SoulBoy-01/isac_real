## 一、三条因模拟结果而产生的修正

### 修正 1：M2 的判据必须与 M1 分开，不能合并成"可用率"

**模拟结果**（`sim_framing_result.csv`）：

| 模式 | p=10⁻² 投递率 | p=10⁻² 失步率 |
|---|---|---|
| M1 裸前缀 | **85.6%** | 0.70% |
| M2 前缀+CRC（原版，丢块） | **73.1%** | 2.07% |
| M3 定长分片 | 100% | 0% |

**原版 M2 在两个指标上都比 M1 差。**

**原因**：
- M1 长度字段错 → 切错位置 → 投递了错位数据 → 字节流**连续但内容错**
- M2 长度字段错 → CRC 检出 → 丢整块 → 字节流**出现空洞**

H.264 解码器对"错位"的容忍度高于"断档"，因此原版 M2 更差。

**结论**：**不能用"投递率"作为 M1/M2 的主判据**，否则结论会被数据反驳。

---

### 修正 2：不能写"M0 失步率 100%"

**模拟结果显示**：M0 的失步率仅 **0.33%**（恒定，不随 p 变化）。

**原因**：M0 一刀切错之后，切出来的块里**偶尔恰好包含起始码**——因为随机数据中 0x00 密集，伪起始码出现率高于理论值 2⁻²⁴。

**正确的表述**：

> **M0 的有效投递率恒为 0%，与 p 无关。**

而非"M0 失步率 100%"。

**这个表述更有力**——它说明 M0 的问题是**结构性的、与误码无关的**。

---

### 修正 3：模拟中 M3 恒定 100% 是"理论下界"，实测必然下降

**模拟中 M3 的有效投递率在所有 p 下都是 100%**，因为模拟只注入了比特翻转，边界靠算术确定，永远不会错。

**真实链路会多两个衰减因素**：

1. **LDPC 整码字失败**：一个 LDPC 块译不出来 → 整个 1024 字节块丢失
2. **块丢失后的字节流空洞**：虽然边界仍正确，但内容缺失

**因此**：
- 模拟曲线是**理论下界**（最好情况）
- 实测 M3 的投递率会随 p 下降，但**失步率应仍为 0 或极低**
- **论文中必须用实测数据作图**，模拟仅作"理论预测"叠加

**写作建议**：图中同时画实测点（实线）与模拟曲线（虚线），说明"M3 的失步率确实为 0，但投递率受 LDPC 块失败影响而下降"。

## 二、主指标与辅助指标的最终定义

**本轮讨论后确定：主判据是"失步"，不是"投递率"。**

| 层级 | 指标 | 定义 | 用途 |
|---|---|---|---|
| **主判据** | 失步率 $N_{\text{mis}}$ | 连续 3 块无起始码，记一次；除以块数 | **M1 vs M2 的核心** |
| **主判据** | 恢复时间 $T_{\text{rec}}$ | 从失步到重新出画的中位数 | M1 vs M2 的次要判据 |
| 辅助 | 有效投递率 | 有效字节 / 总字节 | 吞吐损失；**不能作主判据** |
| 辅助 | 丢块率 | `framing_drop` / 总块数 | 仅用于 M2a vs M2b |
| 辅助 | 序号缺口数 | `seq_gap` | 仅 M3 使用 |

**M1 与 M2 的预期差异（定性，不是定量）**：

| | M1 | M2（改进版） |
|---|---|---|
| 错误性质 | **持续性**（错位一直传播） | **局部性**（只坏这一块） |
| 恢复方式 | 等下一个起始码碰巧对上 | 主动从起点重新寻找 |
| 预期失步率 | 随 p 线性上升 | 显著更低 |
| 预期恢复时间 | 长（要等 I 帧或偶然对齐） | 短（下一块即恢复） |

## 三、M2 的设计缺陷与两个变体

### 原版 M2（M2a）的问题

`decode_one()` 在 `BadCrc` 时直接返回失败，调用方丢块。**这制造了字节流空洞，比 M1 的错位更伤解码器。**

### 改进版 M2（M2b）

**CRC 失败时不丢块，而是"放弃 length 的权威性"，把整个块交给下游，用起始码重新找边界。**

```
M2b 语义：
  CRC 通过 → 按 length 切 → 投递
  CRC 失败 → 丢掉 length → 把整块数据交给下游 → 下游用 00 00 00 01 重新定位
```

**关键区别**：
- M1：相信错误的 length，**继续错位**
- M2a：检出错误，**丢掉整块**（制造空洞）
- M2b：检出错误，**退回不依赖 length 的边界**（局部化损伤）

### 两个变体都要做

| 组 | 设计 | 论文中的角色 |
|---|---|---|
| **M2a** | CRC 失败 → 丢块 | **反例**：证明"单纯丢弃"的代价 |
| **M2b** | CRC 失败 → 交下游重同步 | **正解**：证明"重同步"的价值 |

**M2a 与 M2b 的差异证明**：

> 检错能力本身不够，还要有配套的恢复动作。

**这个对比成本极低**：同一个 CRC 判断之后执行不同动作，代码约 10 行差异。

**若时间紧**：只做 M2b，用模拟数据（本文档修正 1 的表格）说明"若直接丢块会更差"。

## 四、M2b 可能接近 M3，这是好事

**原理**：M2b 在 CRC 失败时退回"从头找起始码"，本质上就是**在一个块内执行 M3 的策略**。

```
M3     ：全程不用 length，靠算术边界
M2b    ：能用 length 就用，不能用就退回 M3 的做法
```

**若实测 M2b ≈ M3 ≫ M1**，论文故事从"三层递进"变为"两强两弱"：

```
M3 ≈ M2b  ≫  M1  ≫  M0
```

**这支持一个更强的论点**：

> **最优策略不是"三选一"，而是"能用长度字段就用，一旦发现不可信，立刻退回算术边界"。**
> 保护的关键不在于"有没有校验"，而在于"**发现不可信之后能否退回一个不依赖该信息的边界**"。

**该论点比"CRC 有用"强得多，且可迁移。**

---

## 五、若被问"M2 和 M3 差不多，M2 存在的意义是什么"

**标准应答**：

> M2 与 M3 的差异不在效果，在**适用性**。
> M3 必须放弃报文边界（所有块定长，补零混入），只适用于**自定界载荷**（如 H.264 Annex B）。
> M2 保留了报文边界，只在失败时退让，因此**对任意载荷格式都适用**，代价是多 2 字节校验。
>
> 即：**M3 更彻底但更专用，M2b 更通用但依赖长度字段的正确性。**

## 七、Framing.hpp 的参数来源说明（澄清记录）

| 参数 | 值 | 来源 | 能否改 |
|---|---|---|---|
| `kPrefixLen = 2` | 2 字节长度 | **沿用作者原实现** | 否（实验变量之一，固定） |
| `kChunkSize = 1024` | 定长块 | **本文设计**（实验变量） | 否（固定后不可调） |
| `kChunkPayload = 1022` | 1024 − 2 | 由上式推得 | 否 |
| `kCrcLen = 2` | CRC16 | 本文设计 | 否 |
| `kMaxPayload = 65535` | 2 字节上限 | 由 2 字节推得 | 否 |
| `kMisalignRun = 3` | 连续 3 块 | **本文设定**，须在论文声明 | **否，写入后不得改** |

**原系统真实约束（已核对代码）**：

```cpp
// OFDMModulator.cpp L1368
std::vector<uint8_t> udp_buf(25200);   // UDP 收包缓冲上限 25200 字节
```

**含义**：平台允许单包最大 25200 字节，**远大于 2 字节长度字段的 65535 表示范围**，因此长度字段不是瓶颈。

**论文中的表述**：

> 定长块取 1024 字节，与"2 字节序号 + 1022 字节载荷"对齐，且不超过平台 UDP 单包上限（25200 字节）。
