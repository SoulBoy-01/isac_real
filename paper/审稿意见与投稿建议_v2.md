## 0. 审稿设置

- **输入范围**：会议版全文（正文 + 表 I–III + 图 1/2/3/5）；长版全文（含 16QAM、CP=64、码率扫描）；图件源文件；感知运行日志。

- **稿件主张摘要**：在 OpenISAC（N320 发 / B210 收）室内链路上跑实时 H.264，(i) 四种 RS(255,K) 外码稳态均零失败，故最轻的 RS(255,223) 已"充分必要"，回收 8.4% 吞吐；(ii) MPEG-TS 容器把残余错误放大 γ≈7（模型）到 4–500（实测），换成裸 H.264 + 容错解码器可解决；(iii) 队列整形把端到端时延钉在 250±0.5 ms，其中射频只占 ≈3 ms。由此提出"最轻量充分保护"设计原则。

## 1. Reviewer 1 —— 物理层 / 信道编码 / 测量严谨性

**总体评价**：这是一份扎实的工程测量记录，但作为论文，核心论断的统计基础不足以支撑其措辞强度。多处数字彼此不自洽，且关键结论（"必要且充分""γ 模型被验证"）在逻辑上不成立。

**谁会关心、为什么**：做 ISAC/SDR 试验台的工程团队会关心"外码到底要留多少余量"这类实测答案——这是本文最真实的价值。

**主要优点**
1. 实测而非仿真，平台、帧结构、编码链参数交代得足够具体，工程可复现性高于同类试验台论文。
2. 把"外码冗余"和"上层放大"放在同一条链上讨论，问题提得对。
3. 诚实地报告了失败实验（16QAM、CP=64），这类负结果对社区有价值。

**主要问题**

1. **"必要且充分"在逻辑上不成立。** 四种配置全部零失败，只能证明"充分"（且是在该工作点上的充分），无法证明"必要"。要证必要性，必须做出"更弱的保护会失败"的对照：至少包含 RS(255,239)、以及完全关闭 RS 的稳态长跑，并扫 SNR 直到出现可见失效。当前证据下，摘要里的 "both necessary and sufficient" 必须删掉，改为 "sufficient at the measured operating point"。
2. **没有 SNR 扫描，就没有 waterfall。** 全文的编码结论只在一个未标明的 SNR 工作点上成立。审稿人一定会问：这个工作点是多少 dB？离 LDPC 门限多远？没有 SNR 横轴，"残余 BER < 5×10⁻¹⁰" 只是一个点估计，无法外推，也无法支撑"Pareto"这个词（Pareto 前沿需要至少两个可权衡的维度上变化的曲线）。
3. **零事件上界的表述不严谨。** 10⁶ 码字 × 255 B × 8 bit = 2.04×10⁹ bit。零错误时，1/2.04×10⁹ ≈ 4.9×10⁻¹⁰ 是**测量分辨率**，不是置信上界；95% 置信上界应按 rule of three 给到 ≈1.5×10⁻⁹。请写成 "no errors observed in 2.0×10⁹ bits; 95% upper bound 1.5×10⁻⁹"，否则会被当成统计错误。
4. **与 5.4 节的数字直接冲突。** 5.4 节取"每 LDPC 块残余失败概率 ≈0.002% = 2×10⁻⁵"。若真如此，10⁶ 块应出现约 20 次失败，而 4.3 节报告零次。两者相差约 1.5 个数量级。这是一处**硬矛盾**，必须二选一：要么 0.002% 是运动场景/另一工作点下的估计（那就必须写明来源工况），要么 5×10⁻¹⁰ 的上界不成立。
5. **Markov 模型算不出自己给的数。** E[T_Search] = 188/(1−3×188p)，代入 p=10⁻³ 得 188/0.436 ≈ **431 B ≈ 2.3 个 TS 包**，而正文写"≈700 B（≈3.7 包）"。公式与数值不自洽，审稿人按一下计算器就会发现。请给出完整转移矩阵、K_lock=3 的文献依据（不能只写 "VLC/ffmpeg default"），并重算。
6. **γ 模型"被验证"是不成立的。** 模型预测 7，实测 4–500（跨 125 倍）。一个落在两个数量级测量散布**中间**的点不叫验证，叫不可falsify。正确写法：模型只刻画"静态头部暴露"这一项，实测差异由解码器状态机解释；并给出**逐栈**的拟合（例如把 γ 分解为 γ_header × γ_state，其中 γ_state 由实测的重新锁定时间估计）。否则建议把模型降级为"量级估计"。
7. **γ 的定义在操作上不闭合。** γ = P_data_loss / p，但压力测试期间 p 从未被测量。当前 γ_TS = 0.995/p 中的 p 是反推出来的，等于循环论证。必须报告每次运行中容器输入端的字节错误率（RS 关闭时在 payload 接口用 PRBS 比对直接测），并给误差棒。
8. **吞吐回收 8.4% 无法复现。** 按你自己的分块方式算：1026 B（含 2 B 长度前缀）在 K=223 时占 ⌈1026/223⌉=5 个 RS 块 = 1275 B 上线；K=191 时占 6 块 = 1530 B 上线。空口效率比 1530/1275 = **1.20，即 +20%**；仅按码率比是 223/191−1 = **+16.75%**；含前缀的净荷比 221/189 = **+16.9%**。三条路都算不出 8.4%（恰好是 16.8% 的一半）。请给出推导，否则这个出现在摘要里的数字站不住。
9. **而且这个增益在你的平台上根本观测不到。** 你自己算了 QPSK 波形容量 ≈38 Mbps，实测可用吞吐只有 3–5 Mbps（差 10 倍，归因于 USB3／丢包策略／填充）。在 USB 瓶颈区，RS 换码不会带来任何可测吞吐变化。所以"recovering 8.4% payload throughput"是一个纸面数字，没有任何端到端测量支持。要么补一组"换码前后实测吞吐"的对照，要么把这句话改成 "reduces on-air overhead by 16.8%（未在端到端吞吐中体现，因受接收机 USB 通路限制）"。
10. **BER 计数器的有效性存疑。** 表 7 的 349 个错误字节，正文解释为"测试头部的非填充字节"，但又说这类只占 ≈0.78%——0.78% 解释不了 349 字节，也推不出"effective payload error rate is near zero"。这个推理是断的。建议直接用 PRBS-23 净荷 + 对齐后逐字节比对，或加 CRC 统计，重新生成表 7。
11. **CP=64 的物理解释不可信。** CP=64 对应 1.28 μs。室内 RMS 时延扩展通常 50–100 ns、最大附加时延几百 ns；1.28 μs 的 CP 对室内多径是**绰绰有余**的。因此"室内反射超出保护间隔导致 ISI"这个因果链在物理上讲不通（除非你能给出实测 PDP）。更可能的原因是：8 导频下 LMMSE 估计 + 时延谱峰值/均值比 20× 门限 + CFO 回归的联合失效（你自己也观察到 95 kHz 的"物理上不可能"的 CFO）。请用 LMMSE 估计出的 CIR 直接画功率时延谱（这份数据你一定有），要么证明附加时延确实 > 1.28 μs，要么把结论改成"同步/估计器失效，而非多径"。
12. **16QAM 的归因有事实错误。** "the B210's embedded processor cannot complete the doubled computation"——B210 没有跑软解映射的嵌入式处理器；OpenISAC 的 C++ PHY（含 max-log-MAP 解映射）跑在**主机 CPU** 上，B210 只是射频前端 + FPGA 抽取。CPU 105% 是主机侧的。请改为主机 CPU/USB3 通路的计算-带宽瓶颈，否则熟悉 USRP 的审稿人会直接判为事实错误。
13. **RS 块与 LDPC 块的对齐没交代。** LDPC(1008,504) 是 126 B 码字，RS 是 255 B 码字，两者不整除；21×48=1008 的交织深度恰好等于一个 LDPC 码字。RS/LDPC/OFDM 帧之间如何映射、填充浪费多少，直接决定你那个 8.4% 和 BER 统计的单位。必须补一段映射说明。

**Nature 式判据对照**：原创性中等偏低（方法均为既有技术的组合）；科学重要性中等（对试验台建设者有实用价值，对 ISAC 理论无推进）；技术可靠性**不达标**（上述 4、5、7、8 为硬伤）；可读性良好。

**推荐倾向**：**Major Revision**（若投期刊）；按现状投任何 SCI 期刊会被拒或直接退回重写。

## 2. Reviewer 2 —— 视频传输 / 容器 / QoE / 系统层

**总体评价**：这是全文最有意思的部分，但实验设计与"视频"这个对象不匹配：全文没有一个客观视频质量指标，容器对比打的是一个稻草人基线。

**谁会关心、为什么**：做实时视频 over 无线链路的工程人员会关心"TS 到底该不该用、哪个解码器抗错"——但他们会要求你给出可比的 QoE 数字和标准基线。

**主要优点**
1. 把"容器放大"作为一个可测量的量 γ 提出来，概念清晰，图 3 的表达力强。
2. 三个解码器栈的对比（VLC 死锁 / ffplay 有界搜索 / GStreamer 静默跳过）是有价值的工程结论。
3. 队列整形消除正反馈时延环的叙述逻辑干净。

**主要问题**

1. **没有任何客观视频质量指标。** "0% / 30% / 95% usable playback" 中的 "usable" 全文未定义，也没有 PSNR/SSIM/VMAF、没有坏帧计数、没有 concealment 后的帧级损伤度量。视频领域审稿人会直接以"结论不可量化"拒稿。最低要求：逐帧 VMAF 或 PSNR 时间序列 + 可见损伤事件计数（并说明判定规则），并报告冻结帧时长分布。
2. **基线选错。** IP 上的 H.264 标准传输是 RTP（RFC 6184），不是 MPEG-TS。MPEG-TS 是 DVB 广播体系的封装。用"TS vs 裸流"作为容器对比，相当于证明"广播封装不适合丢包信道"——这是 2000 年代 DVB-H/MPE-FEC 就已经确立的常识。必须补：RTP/RTSP、SRT 或 RIST、以及至少一个带 NACK/FEC 的现代方案（WebRTC/QUIC）作为基线，否则"7× 放大"的实践意义被高估。
3. **γ 只在一个人为压力区间成立，且这个区间被你自己证明不会发生。** 第 III 节结论是稳态残余 <5×10⁻¹⁰、外码在稳态从不触发；也就是说正常运行中容器层根本看不到错误，γ 无意义。全文真正的因果关系因此是：*在正常工况下，容器选择不影响质量；只有在人为关掉 RS 的压力工况下才影响*。这个逻辑你必须正面写出来并重新定位贡献（"压力工况下的失效模式与恢复行为"），否则审稿人会用你自己的第 III 节反驳你的第 IV 节。
4. **"零错误净荷投递"与表 7 自相矛盾。** 摘要写 "zero-error payload delivery"，同一篇论文表 7 给出 349 个错误字节、BER 0.015%。必须统一口径（建议改为 "zero uncorrected block errors in steady state"）。
5. **时延精度与测量方法不匹配。** 秒表 + 30 fps 拍摄的分辨率是 33 ms，却报告 250.3 ± 0.5 ms（0.2%）。这个 ±0.5 ms 是 4 个被量化样本的标准差（250/250/251/250），既不是抖动测量，也不是置信区间；而 5 分钟内实际观测范围是 233–266 ms、并有 112/38 ms 的异常点。图 2(a) 整个"5 分钟轨迹"只有 8 个点，称不上 trace。二选一：老老实实写 "median 250 ms (range 233–266 ms), resolution ±33 ms"，或者做硬件时间戳（在编码前打入单调时钟、解码后取出，或用光电二极管+示波器测屏），给出直方图与 p99。
6. **时延分解表是估算的加总，不是测量。** 200/27/10/5/2.3/3/5 这些数各自怎么来的没有说明，而且 "ISAC radio ≈3 ms" 与 "OFDM framing 2.3 ms" 明显重叠（3 ms 基本就是一个帧周期 2.304 ms 的复述），合计 252.3 又声称 250。要么给出逐级打点的仪器化测量，要么删掉这张表，只保留"解码器占大头"的定性结论。
7. **"2.5× headroom" 的取点不一致。** 3000 kbps 处 BER 0.0025%，但 2500 kbps 处是 0.0108%（更差）。用最优点宣称余量、却在正文承认关系"非单调且由流水线占用决定"，等于承认这不是链路容量结论。请固定一个 BER 目标（如 ≤1×10⁻⁴），在该目标下定义最大可持续速率。
8. **缺少拥塞/竞争场景。** 没有任何"感知与视频同时满载"的资源分配实验（payload 与 sensing_pilot 的 RE 配比、感知占空比对视频的影响）。这正是 ISAC 场景下最有价值的问题，却完全空白。

**Nature 式判据对照**：跨学科读者兴趣低；对视频传输社区的技术增量中等；方法学（无 QoE 指标、无标准基线）不达标。

**推荐倾向**：**Major Revision**，且必须补客观 QoE 与 RTP 基线；否则只能投工程类 4 区刊。

## 4. 交叉综述

**共识优点**
- 真机实测、平台与参数交代具体；负结果（16QAM/CP）诚实；γ 这个概念提得漂亮；工程结论对做试验台的人有直接用处。

**共识技术风险（按致命程度排序）**
1. **无感知结果** → 与 ISAC 定位不符（R3-1）。这是"投哪里"的决定性因素。
2. **无客观视频质量指标** → 视频类结论不可量化（R2-1）。
3. **数字硬矛盾**：8.4% 无法推导（R1-8）；必要/充分不成立（R1-1）；5.4 节 0.002% 与 4.3 节零失败冲突（R1-4）；摘要"零错误"与表 7 冲突（R2-4）。
4. **模型未被验证**（γ 预测 7、实测 4–500；Markov 公式算不出 700 B）（R1-5/6）。
5. **无 SNR 扫描 / 无重复 / 无置信区间** → 所有"Pareto""上界"结论都只有一个工作点（R1-2/3）。
6. **基线是稻草人**（TS vs 裸流，缺 RTP/SRT/QUIC）（R2-2）。
7. **时延精度与测量方法矛盾**（R2-5/6）。
8. **CP=64 与 16QAM 的物理解释有误**（R1-11/12）。

# 9. 追加分析（第 2 轮：作者澄清两点）

## 9.1 "感知是平台自带、不是我开发的" —— 能写，但必须换写法

**能写，而且应该写。但要把"使用平台能力"和"声称平台能力为贡献"彻底分开。**

这是试验台论文的通行做法：没有人会因为 srsRAN/OAI/GNU Radio/USRP 不是作者写的就拒稿。审稿人拒的是"把别人的模块写成自己的创新"。而且这里有一个现实风险：OpenISAC 的作者完全可能被编辑选为审稿人。

三种合法层次，按投入递增：

| 层次 | 写法 | 是否算贡献 | 风险 |
|---|---|---|---|
| L1 描述 | 在 System Description 里说明感知链在跑、资源块类型可配 | 否（属于实验条件） | 无 |
| L2 表征 | 给一张 RD 图 + 一个已知目标的测距误差（卷尺对照） | 弱（属于"工作点标定"） | 低 |
| **L3 共存** | **payload / sensing_pilot 的 RE 配比扫描；开/关视频时的感知指标对比；video QoE 随之变化** | **是（这才是你的创新）** | 低 |

**L3 是唯一能让你"配得上 ISAC 论文身份"的做法，而且不需要你写任何感知算法**：RE 配比是 OpenISAC 已有的配置项，你只是扫参数 + 测两端。这恰好是 ISAC 社区真正缺的数据（"同波形同时跑实时视频与感知，各自付出什么代价"）。

必须做的归属声明（可直接用）：

> The monostatic and bistatic sensing chains are provided by the OpenISAC platform [4] and are used here unmodified. Our contribution is not the sensing algorithm but the measurement of how a continuous video payload and the sensing resource allocation interact on the shared waveform.

**反过来：如果你不做 L2/L3，就不要再把论文定位成"ISAC 论文"。** 只写"concurrently runs"而无一个感知数字，审稿人（尤其雷达学报这类主场刊）会直接判"挂羊头"。这就是上一轮建议"改定位为强编码链路视频传输测量"的原因。你这条澄清，实际上是替自己做了这个选择：**要么补 L3（约 1–2 周，一次带角反的实测），要么放弃 ISAC 身份。**

## 9.2 "不加 RS 外码，稳态实时视频不可用" —— 这是全文最强的结果，但它推翻了论文的三处表述

这句话如果为真，它比论文现在写的任何一条都更有分量。但它与论文当前的三处核心论断**直接冲突**，必须择一修正：

| 论文现在写的 | 你的观察推出的结论 |
|---|---|
| 4.3 节："LDPC 残余 BER < 5×10⁻¹⁰" | 见下方推算：不成立，真实残余至少高 3 个数量级 |
| 4.4 节："外码在稳态只是瞬态保护，不是主动纠错器" | 外码在稳态**是必需品**，否则视频崩 |
| 摘要："the outer code never fires in steady state" | 应当删除 |

### 9.2.1 先做一个数量级推算

1200 kbps 的视频流，若残余误码率为 p，则每秒约 1.2×10⁶·p 个错误比特。

- 若 p = 5×10⁻¹⁰（论文的声称值）→ **约 28 分钟才错 1 bit**。这个速率下视频完全可用，不会"无法实现"。
- 若"无 RS 即不可用"（按 GOP 30 @20 fps = 1.5 s，需约每 1–2 秒一次可见损伤）→ 需要 p ≈ **10⁻⁶–10⁻⁵**。

**两者差 3–4 个数量级。** 也就是说：你观察到的"无 RS 视频崩"，本身就是"5×10⁻¹⁰ 这个上界是错的"的证据。

### 9.2.2 最可能的机制：计数器口径错了（这是关键）

RS(255,223) 的 t = 16，能纠正 16 个字节错误。若真实残余 BER ≈ 10⁻⁶：

- 每个 255 B 码字（2040 bit）的期望错误数 ≈ 2×10⁻³ → 约 **0.2% 的码字需要纠错**，且全部在 t 以内；
- 按 1200 kbps 算约 588 码字/s → **每秒约 1.2 次纠错事件**，但**零次不可纠失败**；
- 于是计数器显示"零失败"——**如果你的计数器只统计"不可纠失败"，而不统计"发生纠正的码字数/纠正的字节数"，那么"零失败"是真的，而"外码从不触发"是伪结论。**
- 关掉 RS 后：每秒 1.2 个错误字节 → 每 ~0.8 s 损坏一个 UDP 包 → 加上 GOP 1.5 s 的传播 → **视频必然崩**。

这三个数字与你两方面的观察（稳态零失败 + 无 RS 必崩）**完全自洽**。所以最可能的真相是：**残余 BER 约 10⁻⁶，RS 全部纠正，计数器只报了不可纠事件。**

### 9.2.3 三种可能，用一次实验区分

| 假设 | 机制 | 判别实验 | 若成立，论文怎么改 |
|---|---|---|---|
| **A. 计数器口径** | 只统计不可纠失败，纠错次数未计 | 加计数器：`codewords_corrected`、`bytes_corrected`、`codewords_failed` | 删掉 5×10⁻¹⁰；改为"外码利用率曲线"（见 9.2.4） |
| **B. 分帧依赖** | 2 B 长度前缀在 RS 块内，RS 兼任分帧/对齐层 | **RS 直通模式**：保留块结构与长度前缀、仅跳过纠错 | 失效归因改为 framing，γ 需重新归因（现结论混淆） |
| **C. 真实残余** | 误码确实存在且被 RS 全纠正 | 同 A | 同 A |

**决定性实验（成本极低）**：实现一个 `RS_PASSTHROUGH` 编译开关——**保留 RS 的分块与 2 B 长度前缀，只跳过纠错**。

- 若直通模式下视频**可用** → 失效来自 framing（假设 B），你现在的 γ 归因是错的，RS 的价值在"分帧锚点"而非"纠错"；
- 若直通模式下视频**仍崩** → 是真误码（A/C），"外码必需"成立，但"从不触发"必须删。

这个开关同时也让审稿人无法再说"你把 RS 关掉做压力测试是人为造错"——因为直通模式保留了完整的包结构。

### 9.2.4 修好后，这反而变成一篇更好的论文

**新的主张（建议替换现在的三句话）：**

> 1. 在该链路上，外码是**功能性必需**的：完全移除 RS 后稳态实时视频不可用；
> 2. 但外码的**强度**需求远低于部署值：RS(255,223)（14.3%）已足以让视频稳定，更重的配置只是浪费空口；
> 3. 因此存在一条**冗余悬崖**：从 0 到 14.3% 之间存在一个陡峭的可用性跃变，而 14.3% 之后收益饱和。真正的设计问题是"悬崖在哪"，而不是"多留余量"。

这比"外码根本不需要"**强得多**，因为它有因果、有边界、有可操作结论，而且**与你的观察一致**。

配套要补的两件事：

1. **补一个中间点：RS(255,239)（t=8, 6.3%）**。你现在只有 0% 和 14.3% 两个点，悬崖的位置完全未知。加上这一个点，就能画出"视频可用性 / 残余块失败率 vs 外码冗余度"的阶梯曲线——**这才是可发表的知识**。
2. **给 RS 加三类计数器**，报告"需纠错码字比例 vs SNR"。这条曲线同时解决上一轮的 R1-1（必要性证明）和 R1-2（无 SNR 扫描）两个致命意见。

### 9.2.5 连带必须改的地方

- 摘要："making the lightest RS(255,223) both necessary and sufficient" —— 巧合地变得**正确**了，但理由必须换：不是因为"无需纠错"，而是因为"刚好在悬崖上方"。
- 4.3 节：把"10⁶ 码字零纠正"改为"10⁶ 码字零**不可纠**失败；同期纠正 X 个码字、Y 个字节"。
- 4.4 节：删除"外码仅作瞬态同步保护"。
- 8.1 节"reliability cliff"那段其实已经写对了——把它从讨论段提到结果段，作为主结果之一。
- γ 表：补每一组压力测试的实测 p（现在 p 是反推的，见 R1-7）。
- 表 7：如果 RS 全纠正，为什么 payload 接口还有 0.015% 的 BER？这两个必须统一——要么是测试脚本的头部伪错（那就是 0.78% 那句解释错了），要么存在未纠正错误（那就不是"零失败"）。**这是目前最容易被审稿人抓住的自相矛盾。**

### 9.2.6 对投稿的影响

好消息：这些都不需要新硬件、不需要新算法，只需加计数器 + 一个编译开关 + 一次 RS(255,239) 实测，**约 1–2 周**。而它把论文从"我们测了很多，结论是上层更重要"变成"我们定位了一条冗余悬崖，并给出了跨越它的最小代价"——后者在 4 区刊是稳的，在 3 区也有得谈。

# 10. 追加分析（第 3 轮：8 章初稿带来的关键证据）

## 10.1 草稿自己证实了"计数器口径"问题

`chapter3_rs_pareto.md` §3.2.3 原文：

> 解码失败（差错数超过 t）时，降级为透传原始字节。解码器内维护**成功/失败计数器**，每 200 个载荷包输出一次 fail_rate 统计。

这是**成功/失败**计数器——它记录的是"能否解出码字"，而不是"这个码字有没有被纠错"。一个含 1–16 个字节错误、被成功纠正的码字，计数器报的是"成功"。

而 §3.5.2 却写：

> 实际测量中**从未触发过任何 RS 纠正**——所有 255 字节块均以零错误通过。

**这句话不是测量结果，是推断，而且是这个计数器无法支撑的推断。** 你上一轮说"不加 RS 视频不可用"，本身就反证了残余错误真实存在、且被 RS 纠正了。两个观察合起来只有一个自洽解释：**残余错误在，RS 在纠，计数器没记。**

## 10.2 三章之间的 fail_rate 互相打架

| 位置 | 数值 | 含义 |
|---|---|---|
| ch3 §3.4.1 | fail = 1 包（每配置） | "稳态实质为零" |
| ch3 §3.5.1 | "连续数小时未观测到任何稳态字节错误" | 零 |
| ch6 §6.4 表 6-4 | "RS(255,223) **完美纠错**" | 暗示有纠错 |
| **ch7 §7.2.3** | "当前 RS fail_rate **从 10⁻⁵ 级**降至 10⁻⁷ 级" | **非零！** |
| ch7 §7.5 | "将 RS fail_rate 从当前 **0.002%** 降至 10⁻⁷" | **2×10⁻⁵** |

同一篇论文里，稳态失败率被写成 0、10⁻⁵、2×10⁻²（0.002%）。**这不是笔误，是三个不同口径混用。** 审稿人对照章节就能发现。

## 10.3 n = 1 支撑不了"启动瞬态"这个归因

表 3-2 每种配置都是 **fail = 1**，分母却是 100,000 / 38,000 / 88,000 / 250,000。

两点致命的：

1. **帧同步瞬态不会只产生 1 个失败包。** 同步没锁上时，RS 解码器面对的是连续垃圾，失败必然是**成百上千个连续包**。恰好 1 个，更像"某一次随机残余事件恰好超出了纠错能力"。
2. **1 个事件无法区分"瞬态"和"稳态速率~10⁻⁵"。** 在 N=38,000 里 1 次，点估计就是 2.6×10⁻⁵，95% 置信区间是 [0.05/N, 5/N] ≈ [1.3×10⁻⁶, 1.3×10⁻⁴]——**"零"和"1e-5"都落在区间内，数据无法判定**。要判定，必须给每次失败打**时间戳**并跑够 ≥10 次事件。

顺带：四种 t 从 16 到 38 的配置失败率完全相同（都≈10⁻⁵），这说明**失败机制与 t 无关**——那就不是"错误数超过 t"，更可能是分帧/同步类事件。见 10.4。

## 10.4 一个能同时解释全部观察的机制：2 字节长度前缀是单点故障

`chapter3_rs_pareto.md` §3.2.2 原文：

> 为处理可变长度的 UDP 载荷，在 RS 编码前预置 **2 字节的大端序长度前缀**，编码端和解码端均基于此前缀确定原始载荷边界。

这就给出了一个远比"LDPC 残差"更合理的因果链：

| 工况 | 2 字节前缀的状态 | 后果 |
|---|---|---|
| RS 开启 | 前缀在 RS 码字内，**受 t 字节纠错保护** | 前缀永远正确 → 分帧永远正确 → 视频稳定 |
| **RS 关闭** | 前缀**裸露**，1 bit 错即损坏 | 接收端按错误长度切包 → **整条字节流从此错位** → 不是丢一包，而是**后续全部包都错** → 视频永久失效 |

这条链的好处：

- 完全解释"无 RS 即不可用"，而且**不需要**假设荒谬的高 BER（prefix 一旦错，代价是灾难性的、持续性的，不是局部的）；
- 完全解释"四种 t 全部零失败且失败率相同"——只要 t ≥ 1，前缀就被保护，与 t 大小无关；
- 完全解释"计数器只报成功/失败"——前缀错误被纠正，计数器看不到；
- 完全解释 γ 看起来巨大——容器层的放大被 framing 崩塌叠加了。

**如果这条链成立，你的核心结论会从"外码只是瞬态保护"翻转为"外码的主要价值是保护分帧层"，这是一个更强、更有意思、更难被人抢先的结论。**

## 10.5 决定性实验矩阵（约 2 小时，不需要新硬件）

| 组 | 配置 | 目的 | 预期判读 |
|---|---|---|---|
| E0 | RS 关闭（现状） | 基线：失败 | — |
| **E1** | **RS 直通**：保留分块 + 2 B 前缀，仅跳过纠错 | 区分"误码"vs"分帧" | E1 仍崩 → 误码；E1 可用 → 分帧 |
| **E2** | `RS(255,239)` t=8 | 找悬崖上半段 | |
| **E3** | `RS(255,253)` t=1 | 找悬崖下半段 | t=1 可用 → 结论极强 |

同时在 RS 解码器里加四个计数器（每 200 包输出一次）：

```
codewords_total
codewords_corrected      // 发生了纠正的码字数  ← 现在缺的就是这个
bytes_corrected_total    // 累计纠正字节数
codewords_uncorrectable  // 不可纠
```
再给每次 `codewords_uncorrectable` 打时间戳 + 码字序号。

**有了这四行，"残余 BER < 5×10⁻¹⁰" 会立刻变成一个真实的测量**：`bytes_corrected / total_bytes` 是残余 BER 的下界，`uncorrectable / total` 是上界，两者夹住真实值。这个数字比现在那个站不住的 5×10⁻¹⁰ 有说服力得多，而且**直接给出"外码利用率 vs SNR"曲线**——上一轮 R1 提的两条致命意见（必要性未证、无 SNR 扫描）一起解决。

## 10.6 另外两处草稿里暴露的问题

**CP=64 的失锁可能根本不是多径。** `chapter5` §5.3.1 写"两端 YAML 修改 `cp_length`，**不重编译直接重启**"。但 CP 从 128 改为 64 会把帧长从 100×1152 = 115,200 采样（2.304 ms）变成 100×1088 = 108,800 采样（**2.176 ms**，帧率 434 → 460 Hz）。任何以帧为单位硬编码的定时/超时/补偿常数都会失配——尤其 §2.5.4 那个"预测性延迟补偿"就依赖 `samples_per_frame`。**同步崩塌可能只是这个失配，与多径无关。** 要证多径，必须：① 重编译并核对所有帧长常数；② 用 LMMSE 的 CIR 直接画 PDP，证明附加时延 > 1.28 μs（室内几乎不可能）。

**16QAM 归因是事实错误，且草稿里写成"B210 的嵌入式 ARM 处理器"。** B210 上是 Spartan-6 FPGA + USB3 控制器，max-log-MAP 解映射跑在**主机 CPU** 上。把 105% CPU 归因给"B210 的嵌入式处理器"，熟悉 USRP 的审稿人（以及 OpenISAC 作者）一眼就能看出。ch7 表 7-1 里"处理器：嵌入式 ARM → 16QAM LLR 计算过载"同样要改。

## 10.7 对论文主线的最终建议

把"最轻量充分保护"从"外码不需要"改写成**"外码是分帧护栏，而非纠错主力"**：

> 1. 完全不设外码时，实时视频在稳态不可用（分帧前缀无保护，单比特错误即导致流级失步）；
> 2. 只要外码能保护分帧层，视频即可稳定——四种 RS 强度表现完全一致，正说明限制因素不是纠错能力；
> 3. 因此外码的真正作用是"以极小代价锁住帧边界"，14.3% 的部署值可能仍远高于必要值，真正的悬崖在 t=1~8 之间，而非 t=16。

这个版本：有机制、有反直觉、有可操作边界、且**每一个论断都能被上面 4 组实验证实或证伪**。它比"外码根本不需要"稳得多，也比"我们测了很多"有力得多。

# 11. 源码级复查：该仓库的 RS 编解码器从未真正工作

审查对象：`D:\isac\OpenISAC_new`（含 RS 外码的版本；`D:\isac\OpenISAC` 无 ReedSolomon，是上游早期版）。
方法：逐行读代码 + 用 PowerShell 精确复刻 GF(2^8) 表、生成多项式、LFSR 编码与伴随式计算，做数值验证。

## 11.1 三个缺陷（其中一个自我掩盖）

**缺陷 A（致命，且掩盖了 B）：表初始化被函数级 static 门控**

`include/ReedSolomon.hpp:87` 与 `:122`：

    void _init_tables() { static bool done = false; if (done) return; done = true; ... }
    void _init_gen()    { static bool done = false; if (done) return; done = true; ... }

`static bool done` 是**函数级静态变量，所有实例共享**；而 `_exp/_log/_gen` 是**每实例成员**。于是：

- 进程中第 1 个 `ReedSolomon` 对象：表正确；
- 第 2 个及以后：`done` 已为 true，直接返回 → `_exp/_log/_gen` **全为 0**。

而两个调用点都**在每个包的处理路径里新建对象**：

- `src/OFDMModulator.cpp:1128` `ReedSolomon _rs;`（每包一次）
- `src/OFDMDemodulator.cpp:2111` `ReedSolomon _rs;`（每包一次）

数值验证（复刻同一逻辑）：

    rsA（第 1 个实例）: exp 非零 510 个, gen 非零 33 个
    rsB（第 2 个实例）: exp 非零 0 个,   gen 非零 0 个
    rsB 编出的码字: 32 个校验字节全为 0
    rsB 对「3 字节损坏的码字」算伴随式: 32 个全为 0 → 判定"无错误"，原样透传
    透传后 msg[10]: 原值 125 → 收到 39（未纠正，但返回 success）

**后果：除了每个进程的第 1 个包，RS 编码写出的 32 字节校验全是 0；RS 解码永远判定"无错误"，从不纠错、从不失败。14.3% 的冗余是纯粹的浪费。**

**缺陷 B：伴随式的多项式取向与编码器相反**

`include/ReedSolomon.hpp:153-169` 计算 S_i = Σ_j cw[j]·α^(i·j)，即把 `cw[0]` 当作 x^0 的系数。
但编码器把 `msg[0]` 当作**最高次**系数（`cw[0]` = x^254）。正确写法是 S_i = Σ_j cw[j]·α^(i·(N-1-j))。

数值验证（用教科书移位寄存器独立编出合法码字）：

    独立编出的合法码字:  ConvA(当前实现) 非零伴随 = 31/32   ConvB(正确取向) 非零伴随 = 0/32
    C++ LFSR 编出的码字: ConvA = 31/32                      ConvB = 0/32
    → C++ 的 LFSR 编码器本身是正确的；错的是伴随式的取向。

**后果：一旦修好缺陷 A，第 1 个包起每个合法码字都会被判为"有错"，BM/Chien 大概率失败，`decode()` 返回空 → 100% 丢包。也就是说，只修 A 会让系统从"假通过"变成"全失败"。**

**缺陷 C：纠错计数从未被统计**

`src/OFDMDemodulator.cpp:2109`：

    static uint64_t rs_ok = 0, rs_fail = 0, rs_corrected = 0;   // rs_corrected 声明后从未 ++

同时头文件里 `decode_with_stats(..., size_t* errors_corrected)`（`:63-75`）**没有被调用**。所以论文所需的"纠正次数/纠正字节数"在实现里根本不存在。

## 11.2 这解释了论文里全部反常现象

| 现象 | 真实原因 |
|---|---|
| 四种 RS 配置"稳态零失败" | 缺陷 A：表全 0 → 伴随式恒为 0 → 永远返回 success |
| "10⁶ 码字从未触发纠错" | 同上，且 `rs_corrected` 从未累加 |
| "残余 BER < 5×10⁻¹⁰" | 由上一条直接推出的伪结论 |
| **每种配置恰好 1 次失败，且都在 ok<1000** | **第 1 个包用的是正确表，于是撞上缺陷 B，解码失败 → `rs_fail=1`**；此后表全 0，再也不失败 |
| "fail_rate 随 ok 呈 1/n 衰减" | 就是 1/N，构造使然，不是"单次瞬态"的证据 |
| 四种 t 的失败率完全相同 | 失败与 t 无关，因为根本没走到纠错 |

另外 `decode()` 在 `len % 255 != 0` 时直接返回空（`:52`），而 `payload_len` 来自帧头；所以 `rs_fail` 也可能统计的是**帧头长度解析异常**，而非码字错误。无论哪种，它都没有度量"码字解码失败"。

## 11.3 对"不加 RS 视频就崩"的修正

既然 RS 从未纠正过任何字节，那么"关掉 RS 后视频不可用"**不可能**是纠错能力造成的。最可能的原因是**分帧**：

- 编码侧把 `[2 字节大端长度][载荷]` 作为 RS 输入（`OFDMModulator.cpp:1133-1137`）；
- 解码侧从 `rs_decoded[0..1]` 读长度再切包（`OFDMDemodulator.cpp:2118-2123`）。

"关掉 RS"如果同时去掉了前缀写入，接收端就会把 H.264 码流的头 2 字节当成长度 → 每个包被错误长度切分 → **整条流级失步**，而不是局部丢包。这与"视频彻底不可用"的观察完全吻合。

**决定性实验（成本极低）**：编译一个 `RS_PASSTHROUGH` 模式——保留分块与 2 字节前缀，只跳过纠错。
- 若视频**可用** → 失效来自分帧，现论文的 γ 归因需要改写；
- 若视频**仍崩** → 才是真正的误码问题，但那时必须先有一个能工作的 RS 才能谈"需要多强"。

## 11.4 修复建议：不要补，直接换实现

这个解码器从未成功解出过一个码字，逐行修（表初始化 + 伴随式取向 + BM/Chien/Forney 取向 + 计数）风险远高于替换。建议：

1. 换用经过验证的实现：Phil Karn `rs.c` / `libfec`（`encode_rs_8` / `decode_rs_8`，GF(2^8), 0x11D，与本项目参数一致），或 `libcorrect`。
2. 换掉后**先跑单元测试**再上链路：

```cpp
// 10 行自检：编码 → 注入 t 个错误 → 解码 → 必须完全还原
ReedSolomon rs;
std::vector<uint8_t> msg(223);
for (int i = 0; i < 223; ++i) msg[i] = static_cast<uint8_t>(i * 37 + 11);
auto cw = rs.encode(msg.data(), msg.size());
for (int trial = 0; trial <= 16; ++trial) {           // 0..t 个错误
    auto bad = cw;
    for (int e = 0; e < trial; ++e) bad[e * 13] ^= 0x5A;
    uint8_t out[223]; size_t corrected = 0;
    bool ok = rs.decode_with_stats(bad.data(), bad.size(), out, &corrected);
    assert(ok && corrected == (size_t)trial && memcmp(out, msg.data(), 223) == 0);
}
// 17 个错误必须被判定为不可纠
```
3. 修好后加三类计数器：`codewords_total / codewords_corrected / bytes_corrected / codewords_unccorrectable`，每 200 包打印，并给每次不可纠事件打时间戳。
4. `ReedSolomon` 改为成员对象（或 `static const` 表），不要每包构造。

## 11.5 对论文的影响（必须重写第三章，但故事更硬）

- 第三章的"零失败 + 5×10⁻¹⁰ 上界 + 外码仅为瞬态保护"**全部作废**，因为测量对象是一个空转的解码器。
- 但换来的东西更有价值：**"我们实测发现部署的外码实现从未生效；修正后重新测量，才定位到真正的保护边界在分帧层。"** 这是一条有方法学价值的负结果 + 正结果组合，比现在这篇更经得起审。
- 期刊定位不变（4 区 SCI / EI 即达标），但**必须先有一个能通过的单元测试**，否则第三轮审稿人只要问一句"你的 RS 自检通过吗"就会崩。
