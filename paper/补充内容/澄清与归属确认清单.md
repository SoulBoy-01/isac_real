## C-01　平台的"视频业务"是文件推流，不是实时业务

### 事实

上游 README（V1.0 与主分支）给出的视频示例是：

```bash
# 发送：把 mp4 文件按 -re 实时速率推 RTP
ffmpeg -re -stream_loop -1 -i video.mp4 -an -c:v libx264 \
  -x264-params keyint=5 -b:v 3000k -f rtp -sdp_file video.sdp \
  "rtp://<BS_IP>:50000"

# 接收：播放器回放
ffplay -protocol_whitelist file,rtp,udp -i video1.sdp
```

### 作者的澄清

> "当时我做的时候，这个平台能做的视频业务是**传输视频文件**，而不是**实时的视频流传输**。"

### 两者的本质区别

| 维度 | 平台示例：文件推流 | 本文：实时视频业务 |
|---|---|---|
| 视频源 | 本地 mp4 循环播放 | 摄像头实时采集 |
| 时延要求 | 无（ffplay 自带缓冲，晚几百毫秒无感） | 硬约束：≤300 ms 且不累积 |
| 缓冲策略 | 可无限缓冲 | 必须最小化，宁可丢帧 |
| 失效容忍 | 卡顿后回稳即可 | 一次正反馈即不可用 |
| 时延测量 | 无 | 端到端测量 + 分解 |
| 队列设计 | 非问题 | 决定成败 |

### 对论文的影响

**这不是"配置差异"，是研究对象的差异。** 平台的视频功能回答的是"链路能不能把视频数据传过去"，本文回答的是"视频业务能不能以有界时延持续可用"。

**因此以下三条应恢复为贡献**（曾被误降级）：

1. 从零搭建实时视频业务管道（采集→编码→ISAC→解码→显示）
2. 端到端时延测量与分解方法
3. 队列整形消除正反馈（实时场景特有）

### 论文写法（可直接用）

> 现有 ISAC 平台的视频功能停留在**文件推流与播放器回放**层面，未针对实时业务所需的时延约束做设计：无采集链路、无时延测量、无缓冲策略。本文构建了完整的实时视频业务试验床，并建立端到端时延的测量与分解方法。

## C-02　队列深度 32 → 4–8：确认为自研改动

### 证据（代码级）

| 文件 | 上游 `OpenISAC` | 本文 `OpenISAC_new` |
|---|---|---|
| `config/Demodulator_X310.yaml` L9 | `frame_queue_size: 32` | **`frame_queue_size: 4`** |
| `config/Demodulator_X310.yaml` L10 | `sync_queue_size: 32` | **`sync_queue_size: 8`** |
| `config/Modulator_X310.yaml` L68 | `paired_frame_queue_size: 32` | **`paired_frame_queue_size: 8`** |

上游所有 `Modulator_*.yaml` 均为 `tx_circular_buffer_size: 32`、`data_packet_buffer_size: 32`。

### 结论

**"32 → 4–8" 是有据可查的自主改动**，不是记忆偏差。

> 注：主分支 README 的参数表写 `frame_queue_size` 典型值 8，那是**主分支改了默认值**；V1.0 与你所用的基线确实是 32。若被问"32 从哪来"，答：**基线配置的默认值**。

### 为什么这个改动在实时场景才重要

文件推流场景下，ffplay 缓冲几千毫秒都无感，队列深度不是问题；实时场景下 4×32 帧 ≈ 300 ms 且会正反馈。**该问题在平台示例的用法下根本不会暴露。**

## C-03　帧头重复校验：上游自带，非自研

### 证据

| 位置 | 上游 | 本文 |
|---|---|---|
| 发送端 `half1` 递增序列 | L1118–1127 已有 | L1148–1156，相同 |
| `payload16` 重复填充 | L1128–1135 已有 | 相同 |
| 接收端 `all_equal` 一致性校验 | L1991–2002 已有 | L2071 起，相同 |

`header_bytes` 采用"半区填 1,2,3… + 半区重复填 payload16"的结构，接收端比对重复区、不一致则丢帧。

### 结论与替代写法

**不能说"我设计了双长度分工 + 重复校验"。**

但由此得到一个**更好的结论**（见 C-11）：

> 同一系统中，载荷边界信息出现在两处——帧头的块数指示字段采用"重复 + 内码 + 一致性校验"三重保护，而 RS 码字内的原始长度字段仅依赖外码纠错。实测前者从未失效、后者构成单点故障。
> **边界保护的有效性由最弱环节决定，而工程实现中该环节最容易被遗漏。**

## C-04　RS 外码：自研但有三处缺陷

### 三处缺陷

1. **码表初始化被函数级静态标志门控**：`_init_tables()` 中 `static bool done` 由所有实例共享，而 `_exp/_log` 为每实例成员。进程内第一个对象之后所有实例码表全零，编码校验位恒零、译码伴随式恒零，**永远判"无错"**。
2. **伴随式多项式取向与编码器相反**：编码器将 `cw[0]` 视为最高次，伴随式计算视为零次。只修第 1 条会让所有合法码字被判错。
3. **纠错计数器声明未使用**：`rs_corrected` 从未自增，`decode_with_stats` 未被调用。

### 已撤回的结论

- 四种 RS 配置稳态零失败
- 残余误码率低于 5×10⁻¹⁰
- RS(255,223) 回收 8.4% 吞吐
- 外码在稳态只是瞬态同步保护

### 正确表述

- 算法采用标准 RS(255,K)，**实现层改用成熟 FEC 库**（libfec），参数 `init_rs_char(8, 0x11D, 0, 1, nroots, 0)`
- **不可说**：自主设计了 RS 编解码器（教科书算法，不加分；且已撤回）

## C-05　多阶 QAM：自研

### 证据

| 仓库 | `include/Common.hpp` 中 "QAM" 出现次数 |
|---|---|
| 上游 `OpenISAC` | **0**（纯 QPSK） |
| 本文 `OpenISAC_new` | **19** |

本文新增 `enum class ModulationType { QPSK, QAM16, QAM64, QAM256 }`、`parse_modulation_type()`、映射与逐比特 max-log-MAP 软解映射。

### 结论

**这是实打实的自研功能。** 论文中可写"扩展了平台的多阶调制能力"，但注意：**只验证到 16QAM**，64/256QAM 不能声称已验证。

## C-06　分帧模式：自研，且是核心实验

### 证据

V1.0 与主分支的 `Modulator.yaml` / `Demodulator.yaml` 完整参数表中，**无任何** `framing_mode`、`prefix_len`、CRC 相关配置项。

### 设计

```
M0 无锚点   : [payload]                         接收端无法定界
M1 裸前缀   : [2B 大端 len][payload]            按 len 切分
M2 前缀+CRC : [2B len][2B CRC16(len)][payload]  CRC 失败则丢该块
M3 定长分片 : [2B seq][1022B 字节流]            无需 len，块长由配置固定
```

### 埋点（必须实现）

`blocks_total` / `framing_drop` / `seq_gap` / `misalign_events` / `bytes_delivered`

`misalign_events` 定义：连续 3 块内找不到 `00 00 00 01`。

## C-07　首帧冻结不可能是随机误码（算术论证）

### 论证

2 字节锚点 = 16 bit，被破坏概率约 $16p$：

| p | 首帧撞上错误的概率 | 100 包/s 下平均间隔 |
|---|---|---|
| $10^{-6}$ | $1.6\times10^{-5}$ | 约 10 分钟 |
| $10^{-4}$ | $1.6\times10^{-3}$ | 约 6 秒 |
| $10^{-3}$ | $1.6\times10^{-2}$ | 约 0.6 秒 |
| $3\times10^{-2}$ | ≈40% | 才可能"第一帧就中" |

**要让首帧必冻结，p 需 >3%**，与"链路偏稳态"矛盾。

### 结论

首帧冻结**只能是结构性的**——定长块链路上缺少边界约定，与 p 无关。

### 由此得到两种失效模式（本文理论骨架）

| | 模式 A：约定缺失 | 模式 B：锚点失守 |
|---|---|---|
| 触发 | 变长载荷 + 定长块 + 无边界元数据 | 有锚点但被误码破坏 |
| 性质 | **确定性**，首包必失败 | **随机性**，与 p 成正比 |
| 概率 | 1 | $\approx 16p$ |
| 修复 | 建立锚点 | 保护锚点（校验 / 定长化） |

**这条论证不需要任何实验，是纯逻辑结论，应在论文中显著位置使用。**

## C-08　衰减方案：固定 30 dB + tx_gain

### 现状

手上有两个 **Mini-Circuits VAT-30+，固定 30 dB**，不是可调衰减器。

### 方案

X310 发射增益软件可调（约 0–31.5 dB，0.5 dB 步进），**等效于可调衰减器**：

| tx_gain | 相对衰减 |
|---|---|
| 31.5 | 0 dB |
| 25 | ~6 dB |
| 20 | ~11 dB |
| 15 | ~16 dB |
| 10 | ~21 dB |
| 0 | ~31.5 dB |
| 0 + 30 dB 固定 | ~61 dB |

### 判据

找到 $p$ 落在 $10^{-4}$–$10^{-3}$ 的那一档，作为所有消融实验的工作点。**这一步不做，后面全白做**。

## C-11　待补的一条：边界保护强度不一致

### 观察（来自 C-03）

同一系统中，同一类信息（载荷边界）出现在两处，保护强度悬殊：

| 位置 | 保护方式 | 实测结果 |
|---|---|---|
| 帧头 `payload_len` | 重复填充 + LDPC + 一致性校验 | 从未失效 |
| RS 码字内 2B 前缀 | 仅靠 RS 纠错（而 RS 实测未生效） | 构成单点故障 |

### 可形成的结论

> 边界保护的有效性由**最弱环节**决定，而非平均强度。平台作者已意识到边界需要保护（帧头做了重复校验），但同样的顾虑未延伸到 RS 码字内，于是那一处成为唯一裸露的锚点。

### 为什么这条好用

- 不需要声称"我发明了机制"，**无归属争议**
- 是**设计准则级别**的洞察，高于"我加了个前缀"
- 有**代码级证据**（两处代码摆在一起，强度差异一目了然）
