## 逐条评判

### 第 1 题：为什么视频必须切成包

**✅ 对的，但只说了一半。**

"网络只能按包传输"是正确的——UDP/IP 协议栈的交付单位是数据报，物理层再把它切成帧。这是**协议规定**，不是实现选择。

**依据**：RFC 768（UDP）规定数据报是独立传输单位；IP 层 RFC 791 规定每个 IP 包最多 65535 字节（含头）。

**但还差一层**：为什么协议这么规定？

因为**网络设备（交换机、路由器）需要"存储-转发"**：收到完整包才转发，才能做校验、查路由表、排队调度。如果允许"连续字节流"，中间节点就无法判断何时可以开始转发。

**这半句在论文里的作用**：说明"切包不是工程偷懒，是架构必然"，从而为"边界问题无法回避"做铺垫。

---

### 第 2 题：三种边界约定

#### ① 定长

**你的答案**："会丢失边界，比如 MPEG-TS"

**⚠️ 部分正确，但结论正好相反。**

MPEG-TS 用定长（188 字节），它的**优点恰恰是"边界永远不会丢"**。你的说法应该是把"缺点"搞反了。

**正确的表述**：

| | 定长（MPEG-TS） |
|---|---|
| 边界由什么决定 | **算术**：第 i 个包从 `i × 188` 开始 |
| 误码能否破坏边界 | **不能**——188 这个数不在数据里，误码改不了它 |
| 真正的缺点 | **浪费带宽**：最后一包不满要补齐；且长度不可变，小包也占 188 字节 |

**为什么 MPEG-TS 选 188**：这个数字是 4 字节包头 + 184 字节载荷，而 184 = 4 × 46（MPEG-2 音频帧长），是为了让音频和视频能整齐复用。

**依据**：ISO/IEC 13818-1 附录 B。历史来源是 DVB 为兼容 ATM 的 47 字节单元（188 = 4 × 47）。

> **这一条在你的论文里极其重要**：M3（定长分片）之所以"永不失步"，就是因为它的边界和 MPEG-TS 一样，是**算术决定的，不在数据里**。

#### ② 长度前缀

**你的答案**："这个前缀的字节可能会在传输过程中损坏"

**✅ 完全正确，而且抓住了要害。**

补充两点：

**第一**：不只是"可能损坏"，而是"一旦损坏，后果会传播"。这就是失步（见第 3 题）。

**第二**：长度前缀还有一个隐含限制——**它能表示的长度有上界**。2 字节最多 65535，如果你想传 100 KB 的包，2 字节就不够。

**依据**：你的代码 `Framing.hpp` 里 `kMaxPayload = 0xFFFF`，就是这个限制的体现。

#### ③ 分隔符

**你的答案**："比如 H.264 给的 0x0001，缺点计算比较慢"

**⚠️ 例子写错了，缺点也说偏了。**

**例子更正**：H.264 Annex B 的起始码是 **`00 00 00 01`（4 字节）或 `00 00 01`（3 字节）**，不是 `0x0001`。

**依据**：ITU-T H.264 附录 B.1.1 定义 `byte_stream_nal_unit()`，起始码为 `0x000001` 或 `0x00000001`。

**"计算比较慢"这个判断需要辨析**：

- **找分隔符确实比"读长度"慢**，因为要逐字节扫描
- **但"慢"不是它的主要缺点**。在 1200 kbps 的视频流上，扫描几个 KB 的字节在现代 CPU 上是微秒级，几乎可忽略

**真正的缺点有两个**：

| 缺点 | 说明 |
|---|---|
| **① 误判风险** | 如果载荷数据里恰好出现 `00 00 00 01`，会被误认为新边界。所以编码器要做"防竞争字节插入"（emulation prevention） |
| **② 必须先找到标记才能开始** | 如果数据开头就是垃圾（比如失步后），接收端要扫很久才能撞上第一个标记 |

**依据（防竞争字节）**：H.264 规定，当 NAL 载荷中出现 `00 00 00`、`00 00 01`、`00 00 02`、`00 00 03` 等序列时，在第三个字节前插入 `0x03`，避免被误认为起始码。这是 ITU-T H.264 附录 B.1.2。

## 更正与补充：失步到底怎么发生

### 一句话

> **长度字段错 1 个比特，不是"丢一个包"，而是"此后所有包都错位"。**

### 逐步演示

发送端要发三个包，每个 1000 字节：

```
包1: [03 E8][1000 字节]     0x03E8 = 1000
包2: [03 E8][1000 字节]
包3: [03 E8][1000 字节]
```

接收端正常流程：

```
读 2 字节 → 0x03E8 = 1000 → 读 1000 字节 → 交出去
读 2 字节 → 0x03E8 = 1000 → 读 1000 字节 → 交出去
...
```

现在包 1 的**最低位被翻转**（0xE8 → 0xE9）：

```
包1: [03 E9][1000 字节]     0x03E9 = 1001
```

接收端的反应：

```
读 2 字节 → 0x03E9 = 1001 → 读 1001 字节 → 交出去
                              ↑
                         多读了 1 字节！
```

**多读的那 1 字节，是包 2 的第一个字节。**

于是包 2 的解析起点变成了"原包2的第 2 个字节"：

```
包2 的"长度字段" = 原包2第2字节 + 原包2第3字节
```

**从此每一个包都错位，而且错位会累积。**

### 关键概念：为什么会"累积"

因为**每次解析的起点，取决于上一次的长度判定**。一旦某次判定错了，起点就永久偏移。

用数学语言：

$$x_{i+1} = x_i + 2 + L_i$$

其中 $x_i$ 是第 $i$ 个包的起始位置，$L_i$ 是从数据里读出的长度。

**如果某个 $L_i$ 读错了，$x_{i+1}$ 就错，然后 $x_{i+2}$、$x_{i+3}$……全错。**

这就是**状态依赖**：解析是串行的、有状态的，错误会传播。

### 对比：为什么定长不会累积

$$x_{i+1} = x_i + 1024$$

**1024 不来自数据，来自配置。** 误码改不了它，所以误差不会累积。

### 这个现象的学术名称

| 领域 | 叫法 |
|---|---|
| 通信/协议 | **帧失步（framing error）/ 失步（desynchronization）** |
| 视频编码 | **bitstream desynchronization** |
| 网络安全 | **parser differential / request smuggling**（同一份数据被两层解析器用不同规则解析） |

## 这一轮新增的概念（术语表）

| 术语 | 英文 | 含义 |
|---|---|---|
| 帧失步 | framing error / desync | 接收端对边界的判断与发送端不一致，且错误会传播 |
| 长度前缀 | length prefix | 用固定字节数表示后续数据长度 |
| 定长分片 | fixed-size chunking | 每个包长度固定，边界由算术决定 |
| 分隔符 | delimiter / sentinel | 用特殊字节序列标记边界 |
| 起始码 | start code | H.264 的 `00 00 01` 或 `00 00 00 01` |
| 防竞争字节 | emulation prevention byte | 防止载荷中出现与起始码相同的序列 |
| 状态依赖 | state dependence | 后一次解析依赖前一次的结果，因此错误会传播 |

## 三个必须记住的对照

### 对照 1：三种边界的"边界在哪"

| 方法 | 边界信息存在哪 | 误码能否破坏边界 |
|---|---|---|
| 定长 | **配置里**（1024、188） | **不能** |
| 长度前缀 | **数据里** | **能** |
| 分隔符 | **数据里**（找标记） | 能（会误判或找错） |

**一句话**：**边界信息在数据里，就一定会被误码破坏。**

---

### 对照 2：你的四个实验模式在做什么

| 模式 | 用了哪种边界 | 边界信息在哪 | 预期 |
|---|---|---|---|
| **M0** | **没有** | — | 必然失败（不知道怎么切） |
| **M1** | 长度前缀（裸） | 数据里 | 误码 → 失步 |
| **M2** | 长度前缀 + 校验 | 数据里 | 误码 → 能检出，但要不要丢块是个设计问题 |
| **M3** | **定长** | 配置里 | **不会失步** |

**这就是整篇论文的骨架。** 四个模式不是随手设计的，而是**"边界信息放在哪里"的四种答案**。

---

### 对照 3：为什么 M0 必然失败

M0 没有任何边界信息，接收端唯一能用的线索是**帧头的 `payload_len`**。

但那个字段的语义是"RS 编码后有多少字节"，不是"原始载荷有多少字节"。**用它去切原始载荷，长度必然不对。**

所以 M0 不是"偶尔失败"，而是**每次都失败**——这与误码率 p 无关。

**这一点在模拟中已得到验证**（`sim_framing_result.csv`）：M0 的投递率在所有 p 下都是 **0%**。

## 单位约定（全文档统一，2026-10-23 补）

**本篇及后续所有 Q&A 中，除非特别声明，$p$ 一律指"字节错误率"（含错误的字节数 / 总字节数）。**

在此约定下，"某字段被破坏"的概率 = **该字段的字节数** × $p$：

| 字段 | 长度 | 被破坏概率 |
|---|---|---|
| 2 字节长度前缀 | 2 字节 | $\approx 2p$ |
| 2 字节长度 + 2 字节 CRC | 4 字节 | $\approx 4p$ |
| MPEG-TS 一个 UDP 内的 7 个同步字节 | 7 字节 | $\approx 7p$ |

**若把 $p$ 当作比特错误率**，则 2 字节字段应为 $16p$。两种写法都对，但**全文必须统一，不能混用**——这是审稿人容易抓的细节。

> **本约定产生的经过**：早期讨论中曾用"16 bit → 16p"（把 $p$ 当比特错误率）与"2 字节 → 2p"（把 $p$ 当字节错误率）混用。二者相差 8 倍，虽不影响定性结论，但会导致数字对不上。现统一为字节错误率。
